# 四组安全修复的升级与验收

本次范围是资源生命周期与内置对象保护（#56、#62 部分）、MFA 首次绑定与恢复（#57、#51 部分）、安全状态并发保护（#54、#52 部分）、APISIX 部署加固（#13、#59 部分）。它不代表这些复合 issue 的全部内容已经完成。

## 数据库升级

已有部署先备份数据库、停止 Host 和 Workbench 写入，再按顺序运行：

```bash
psql "$NEXUSAUTH_DATABASE_URL" -v ON_ERROR_STOP=1 -f database/migrations/20261101_01_resource_integrity.sql
psql "$NEXUSAUTH_DATABASE_URL" -v ON_ERROR_STOP=1 -f database/migrations/20261101_02_mfa_recovery.sql
```

两份脚本都在事务内执行，可重复运行。新数据库继续使用 `production-init.sql`，不需要再运行升级脚本。应用不会自行执行数据库升级。

第一份脚本遇到重复 audience 或孤儿引用会终止，不会替管理员决定删除哪些历史数据。先根据错误定位重复资源或失去关联的授权，再制定数据修复方案、备份并重试。原演示种子有重复 audience，新的种子已经修正；已有演示库仍需先处理重复项。

资源 audience 现在全局唯一且创建后不可修改。升级会补齐现有 AllowedScopes 对应的资源关联；删除资源、撤销关联后，不会因创建同名 audience 自动恢复原授权。客户端、资源及凭据/用户的并发冲突需要重新读取后再提交，不应无限重试旧快照。

Workbench 启动时会标记其配置托管的客户端和资源。管理 API 拒绝修改、删除或重置这些对象，Dashboard 显示为只读；应通过部署配置管理它们。更换 audience 需要单独的数据迁移，不能直接编辑已有资源。

用户和凭据的并发控制使用 PostgreSQL 自带的 `xmin`，无需新增普通版本列。账号认证门控使用 PostgreSQL advisory lock，同一账号的并发认证请求会快速失败，客户端可提示稍后重试。

## MFA 首次绑定与恢复

- 启用 required TOTP 后，尚未绑定的用户先验证密码或邮箱验证码，再进入临时绑定页面；确认动态码前不签发 SSO 会话。注册入口也遵守该要求。
- 带用户验证（UV）的通行密钥视为满足此策略。required 模式强制 WebAuthn 请求使用 `UserVerification=Required`，只完成凭据持有校验的通行密钥不能绕过要求。
- 首次绑定成功展示十个单次恢复码；已绑定用户可在“身份验证器”页面重新验证后生成新码。新码会替换旧码，明文只在本次页面展示，数据库只保存哈希。
- 登录、邮箱操作和密码找回可使用恢复码代替动态验证码。恢复码按用户隔离且只能消费一次，错误尝试仍受账号锁定约束。
- Workbench 的“重置第二因子”需要填写原因。它会撤销 TOTP、通行密钥、恢复码和现有会话，保留账号的启用/禁用状态，并把操作者、目标、原因与时间写入专门的恢复审计表。
- 密码/第二因子重置会使旧的待绑定流程失效。required 模式下，重置后的用户下一次登录会重新进入绑定流程。
- 页面会提示无法解密的 TOTP 密钥。应继续备份并共享 Data Protection 密钥；恢复码和管理员恢复流程不是密钥备份的替代品。

恢复审计位于 `nexusauth.second_factor_recovery_audits`。本次没有实现 #61 的通用管理审计查询功能。

## APISIX

见 [APISIX 网关对接手册](13-APISIX网关对接手册.md)。启动前必须显式配置管理 key 和稳定的字段加密 key；不要在重启时随机更换已有加密 key。

etcd 仅连接专用内部网络，APISIX 同时连接网关网络和内部网络。旧 Dashboard 3.0 直接写 etcd，不能保证敏感字段通过 APISIX 加密，因此本次移除该服务，使用 Admin API 管理。

开启字段加密不会自动转换已有 etcd 中的明文配置。升级前备份，升级后通过 Admin API 重写含敏感字段的配置，并验证 OIDC 登录和令牌操作；旧字段加密 key 也应纳入备份。

## 验收重点

1. 新库初始化和旧库两份升级脚本均成功；重复执行不会破坏数据，重复 audience/孤儿数据会阻止升级。
2. 托管资源不能在管理 API 中变更；删除普通资源并用相同 audience 重建后，旧客户端没有隐式授权。
3. required 模式下登录、注册、首次绑定、UV 通行密钥和恢复后重新绑定均正常。
4. 同一恢复码并发使用只能成功一次；管理员重置失败时事务回滚，不留下部分撤销。
5. 并发的凭据使用、SCIM 更新或登录成功不能覆盖管理员刚设置的吊销、禁用或账号锁定。

后续仍需单独处理邮箱归属/SCIM 连接隔离、验证码与 HTTP 限流、会话/登出语义、通用管理审计、其他部署凭据和 CI/容器加固。只修复上述子项的 PR 不应自动关闭包含剩余工作的 issue。
